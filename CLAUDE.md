# Mindaptive Responder

A self-hosted dashboard that helps Andrew (Mindaptive.ai) follow up with Smartlead leads: it surfaces leads with no contact in 3+ days, drafts a follow-up with Claude on click (single or bulk), and lets him review/edit/send from a browser. Lead replies still auto-draft immediately so hot leads get a fast response.

## Where to make changes for better messages (start here)

These are plain markdown files, not code — edit them directly, no Python knowledge needed:

- **`prompts/human-writing.md`** — **the house voice, and it outranks every other style instruction in the app.** Derived from *You're a Human, So Write Like One* (The Intuitive Writing School): third-grade reading level, contractions, active voice, write to one person, no "Regards", no jargon, no em dashes, uneven sentence rhythm. `app/writing_rules.py` loads it and appends it to *every* prompt that generates text — outreach drafts, auto-reply nudges, translations/localizations, the campaign-fragment translator, and the campaign analysis reports. Nothing else in the app is allowed to define tone; if `prompts/system.md` and this file disagree, this file wins. Add a rule here and it binds everywhere at once. It also defines the **bold convention** — the model marks the one phrase worth noticing with `**double asterisks**` and the app turns those into real `<strong>` (see §11 below).
- **`prompts/system.md`** — the SDR system prompt. Role, tone rules (Hormozi-style: brief, peer-to-peer, no pricing over email), the website-diagnostic framework, objection handling, output format, and the follow-up examples (section 12). This is the first place to change *what* the AI says; `human-writing.md` governs *how* it says it.
- **`knowledge/solutions-catalog.md`** — every product/solution Mindaptive sells, organized by the RACE framework, with per-niche packages. Add or update offerings here.
- **`knowledge/vsl-transcript.md`** — the AI-secretary VSL transcript (home-services installers); referenced when deciding whether to send the video link.
- **`knowledge/lead-gen-vsl-transcript.md`** — the lead-gen VSL transcript (B2B SaaS / consulting / branding agencies), for Mindaptive's *second* product line: running the AI outbound engine for other companies. Mindaptive sells inbound AI **and** lead gen; `prompts/system.md` §1 names both, §5 diagnoses B2B-vs-consumer first, and §7 picks between the three videos by audience.
- **`knowledge/vsl-clinics-trasncript.md`** — the clinics VSL transcript (dental / medical / aesthetic / physio / chiropractic / vet), covering the clinic AI secretary and the treatment-plan follow-up system. **Every clinic that wants a video gets this one** — §7's rule for it is deliberately unconditional, unlike the other two which each need a vertical *and* a diagnosed solution to match, because a clinic can only be a fit for the clinic video and the failure mode being prevented is a dentist receiving the furnaces-and-solar-inverters one. Each transcript carries its own Loom URL in the file, so the model can only send a link it has the audience notes for.
- **`knowledge/hormozi-communication-style.md`** — sales philosophy/scripts reference (objection handling, follow-up cadence patterns).

`app/drafter.py` concatenates `prompts/system.md` + a short "output contract" addendum (instructs the model to wrap its triage/draft/translation in `<triage>`/`<draft_original>`/`<draft_english>` tags so the app can parse them) + all of `knowledge/*.md` + `prompts/human-writing.md` into the system prompt sent to Claude. The house voice goes **last**, so it is the most recent instruction in context when the model starts writing. Adding a new `.md` file to `knowledge/` automatically includes it — no code change needed.

## A second client (AeroDefense)

The responder is **one Smartlead account per process** by design — only Campaigns analysis is multi-account (`app/accounts.py`). So a second client is a **second container off the same image**, not tenancy threaded through the code:

```
docker compose up -d            # app (Mindaptive, :8080) + app-aerodefense (:8081)
```

`app-aerodefense` reads `.env.aerodefense` (see `.env.aerodefense.example`) and mounts `./data-aerodefense:/data`, so the two databases, upload dirs, models, cadences and webhook secrets never touch. Everything that differs was already an env var except the asset paths, which `app/client_assets.py` now resolves:

| `CLIENT_DIR` | prompt / knowledge / signatures | personas |
|---|---|---|
| unset (default) | `prompts/`, `knowledge/`, `signatures/` at the repo root — **byte-identical to before** | hardcoded map in `app/signatures.py` |
| `clients/aerodefense` | `clients/aerodefense/{prompts,knowledge,signatures}` | `clients/aerodefense/personas.json` |

Files fall back to the repo root when a client doesn't override them, so a client only ships what actually differs.

**Adding a third client:** `clients/<slug>/` with `prompts/system.md`, `knowledge/*.md`, `signatures/*.html`, `personas.json`; a `.env.<slug>`; a compose service. No code change.

### What's specific to AeroDefense

- **Template-driven.** `clients/aerodefense/knowledge/response-templates.md` holds the seven approved replies (Security Integration / Airports / Police departments / Events & Venues / Farms, most in *more-info* and *video-demo* variants). `prompts/system.md` maps the real campaign names onto them (`Airports` → Airports, `EggFarm` → Farms, `Stadiums` → Events & Venues, `Executive Protection` → no template, write from the knowledge base) and requires the model to name its choice in `<triage>` so a wrong pick is visible before sending. Add a template by adding a heading to that file.
- **Per-persona booking links.** The three personas (Andrew Grasso, Amy Muschler, Max West — verified as the only `from_name`s across all 129 AeroDefense mailboxes) each have their own HubSpot link. The templates end with one, so `pipeline.create_draft` and `batch_gen` resolve the persona **before** calling the model and pass `sender_name` + `calendar_link` into the prompt — not just the signature afterwards.
- **English only.** `clients/aerodefense/prompts/output-contract.md` overrides the default contract and tells the model to leave `<draft_english>` empty.
- **Its own house voice.** `clients/aerodefense/prompts/human-writing.md` overrides the root one, which bans "Best regards" and mandates a third-grade casual register — wrong for airport ops directors and police chiefs, and it contradicts the approved templates. Template fidelity outranks style there.
- **No pricing, ever**, in any form — acknowledge and push to the 15-minute call.
- **`REQUIRE_KNOWN_SENDER=true`.** AeroDefense rotated through mailboxes Smartlead no longer returns (e.g. `anna@aerodefensemarketing.com`). A thread whose last outbound message came from one is dead — there's no live mailbox to reply from — so it is skipped at scan and aborted at send. Off by default, so Mindaptive keeps just going without a signature. Deliberately re-derived from Smartlead's live list each pass rather than stored as a terminal lead status, so an API blip can't permanently retire a live lead.

## How a message actually gets generated

1. **Daily scan** (`app/scheduler.py: run_daily_scan`) — cron job (`DAILY_SCAN_HOUR_UTC`), Smartlead API only, no Claude. Also triggerable on demand from the dashboard ("Rescan now" button → `scheduler.trigger_scan_in_background`, lock-protected so it can't stack). For every "Interested" lead it checks the thread and decides: due for a follow-up (per the `FOLLOWUP_WAIT_DAYS` cadence list, under the follow-up cap — plus a one-shot revival touch every `REVIVE_AFTER_DAYS` after the cap) → adds a row to the `candidates` table; lead's message unanswered → auto-drafts a reply immediately (fast response to hot leads); otherwise → nothing. Leads in Smartlead's **"Meeting-Booked" category** (matched case/punctuation-insensitively, `MEETING_BOOKED_CATEGORY_NAME`) get frozen instead: status `booked`, open drafts → stale, candidates dismissed, `booked_at` recorded (`db.mark_lead_booked`) — and un-frozen automatically if the category later moves back to Interested. Booked leads stay visible in the inbox with a green "Meeting booked ✅" badge.

    **The scan is two passes, split by cost, and bookings are recorded in the cheap one.** Pass one only *lists* leads (one paginated call per campaign, no per-lead network) and writes every booked lead as it goes; pass two does the expensive part, a thread fetch per interested/auto-reply lead. They used to be interleaved with only `_process_lead` guarded, so anything raising out of `list_campaign_leads` or a thread fetch — a 429, a timeout — killed every *remaining campaign* for that run. It ran that way unnoticed for two weeks: campaigns are walked newest-first, the run died around the fifth each night, and every older campaign stayed frozen at its state from the last complete pass. 34 of the account's 36 Meeting-Booked leads were in those older campaigns and had no `leads_state` row at all, so they were missing from the dashboard entirely (found 2026-08-04). A booking is the one thing the scan records that has no other source, hence recording it before anything costly can fail. Two consequences worth keeping: a campaign that fails to list is counted, and `clear_stale_open_candidates` is **skipped** when any did — clearing "no longer due" against a partial pass would dismiss the open candidates of every campaign that didn't get listed. And a booked lead with no summary yet gets **one** thread fetch, the first time it's recorded, because otherwise it sits in the inbox as a bare name with no date or preview; the steady state stays free.

    **A booking also un-hides the lead** (`db.mark_lead_booked`). Archive and snooze are the only two things that keep a booked lead out of `list_inbox` — a scheduled draft is the third and the same function stales it — so a lead archived or snoozed weeks earlier who then booked stayed invisible under the Meeting-booked filter no matter how often the scan ran; 2 of the 36 were exactly that. The archive is cleared only when it is **older than `booked_at`**, i.e. stale relative to the booking: archiving a lead *after* the meeting is deliberate cleanup, and clearing that every pass would resurrect it nightly with no way to make it stay gone. Writing the rule against the timestamps rather than "only on the transition into booked" is what also repairs rows already in this state — they never transition again, so a transition-only rule would leave them hidden forever. A snooze is always cleared while booked: it says "not now" rather than "put this away", the booking answers it, and it carries no timestamp of its own to age against.
    **A reply must never wait on Smartlead's category.** The scan above only records leads Smartlead has already tagged `Interested` — but Smartlead assigns that with its own AI *after* the reply lands, so at the moment a lead first answers they typically have no category at all. That made a lead's **first** reply invisible: the scan skipped them, `run_reply_catch_scan` reads `leads_state` and they had no row there yet, and the webhook only fires for replies n8n judged relevant. Measured 2026-08-11: of the 20 most recent replies in the Smartlead inbox, 16 had no row in the database, 7 of those purely because Smartlead hadn't categorised them. "Rescan now" appeared to fix it only because by then Smartlead had usually caught up. So `scheduler.run_new_reply_poll` (`NEW_REPLY_POLL_SECONDS`, default 60s) asks the opposite question — not "who is Interested?" but **"who has written to us lately?"**, one `smartlead.list_recent_replies` call across all campaigns — and adopts anyone missing. Only explicitly negative categories are skipped (`_SKIP_ADOPT_CATEGORIES`); **"no category" deliberately is not one**. Two API calls and no per-lead work, which is why it runs on its own fast schedule rather than the reply-catch pass's. Full history in `docs/reply-visibility-log.md`.

    **Spotting a reply is not the same as showing it** (`db.mark_lead_replied`). The inbox list reads `category`, `last_message_preview` and `last_message_at`; `run_reply_catch_scan` used to write none of them and go straight to generating a draft, so a lead who had answered kept the row, chip, preview and list position the last daily scan gave them — the answer was written and the screen said nothing had happened. Every path that learns about an inbound message now goes through that one function, and the catch-scan calls it **before** its has-draft checks, because a message the webhook already drafted for still has to be visible as a message. It also un-archives and un-snoozes on the same timestamp rule `mark_lead_booked` uses.

    **No model call holds a database transaction.** `webhook._process_reply` used to run entirely inside one `db.db_session()`, which commits at exit — so the `interested=1` write landed minutes later, after a Claude call with web search, and until then the lead did not exist for any other connection. An open SQLite write transaction is also an exclusive writer lock (WAL allows one writer), so that same wait blocked the scan, sends and other webhooks; that is what made "Rescan now" crawl. The webhook, the reply-catch pass and `_process_lead` all commit the summary first and open a fresh session for the draft.

2. **Overnight batch pre-generation** (`app/batch_gen.py`, `AUTO_GENERATE_FOLLOWUPS=true` — approved on-by-default 2026-07-19) — right after the scan, every open follow-up candidate whose lead already has `research_summary` is submitted as ONE Anthropic **Batch API** job (50% token cost; no web tools, since a batch result can't continue a pause_turn loop — leads without research stay open for interactive Generate). A 5-minute poll job consumes finished batches: each result is race-checked against a fresh thread, then stored through the same `pipeline.store_draft_result` as interactive drafts. Sending still always requires Andrew's click; only if `AUTO_SEND_FOLLOWUPS` is also on do these drafts go straight to `scheduled` for the lead's next weekday morning.
3. **Generate / Bulk generate** (`app/candidates.py`) — user-triggered fallback for anything not pre-generated. Re-fetches the thread fresh (race-check: skip if the lead already replied), then calls `app/pipeline.py: create_draft` → `app/drafter.py: generate_draft`, which calls Claude with web search/fetch tools enabled so it can research the lead's website (capped: `max_uses: 4` each, fetches ≤10k tokens, and the growing tool-loop conversation carries a `cache_control` breakpoint so pause_turn continuations read prior turns at ~0.1×). Bulk generate runs in a background thread so it doesn't block on Cloudflare's ~100s tunnel timeout.

    **When generation fails, the dashboard says why** (`candidates._last_error` → `generation_error` on `GET /api/leads/{cid}/{lid}` → the client's error note). Generation runs in a background thread, so the HTTP response is `{"started": true}` long before anything can go wrong, and the poll could previously only tell "no draft" — printing *"Could not generate a draft for this lead"* for a missing API key, an empty thread and a model that ran out of budget alike. The reason is kept in memory, keyed per lead, cleared when the next attempt starts. Because it can now relay a provider's own error text, the client renders it with `textContent`, not `innerHTML`.

    **A failed generation costs nothing.** `api_generate` used to retire the open draft *before* starting, so a regenerate that then failed destroyed the message it was supposed to improve: the editor was replaced by an error line, and a second attempt had no `base_draft` to revise — so the steering note applied to nothing and the model rewrote the same email, which reads as "it just gives me the old one back". The old draft is now retired by `db.retire_other_open_drafts`, called from `generate_for_lead` only once the replacement is stored.

    **Reasoning models bill thinking against `max_tokens`.** `_OPENROUTER_DRAFT_MAX_TOKENS` is 16000, not the 4096 that suits a plain chat model: DeepSeek V4 Pro on this output contract (triage + draft + English + research, after a long objection thread) can spend the whole budget reasoning and return no answer at all — `openrouter.complete` detects exactly that and raises. It's the same trap as `ANTHROPIC_MODEL`'s adaptive thinking and `_REPORT_MAX_TOKENS`. It fails per-lead, not always, which is what makes it look arbitrary: the harder the reply is to think about, the likelier the budget runs out first. The final follow-up before the cap is steered into the Section-12 "closing this file" breakup pattern; post-cap revival drafts get fresh-angle steering (`followup_stage` in `pipeline.create_draft`).
4. **Signature** — `pipeline.create_draft` looks up which mailbox sent the thread's last message (`detector.last_sender_email`) and stores that persona's HTML signature (`app/signatures.py`, files in `signatures/`) in the `drafts.signature_html` column. The signature is **kept out of `body_html`** — `body_html` holds the message body only. The signature is shown in the dashboard as a separate read-only preview under the editor (`app/static/app.js: renderDraftSection`, visible in both the Original and English tabs) and is appended **once, unchanged**, at send time in `scheduler.compose_send_body`. This deliberately keeps the signature out of the English translate/localize round-trip: it used to be baked into `body_html`, which meant the English tab translated the signature and `api_draft_localize` then appended a second copy — producing two signatures, one mangled. Because `body_html` is now guaranteed signature-free, the append in `compose_send_body` is a plain, deterministic append (guarded by a substring check only to protect any pre-change draft that still has it baked in). Persona is detected from Smartlead's own `from_name` on each of the 90+ rotating sending accounts (`GET /email-accounts`), not a hand-maintained email list — see `PERSONA_FILES` in `signatures.py` if a new persona/name is added.
5. **Lead research** — the same Claude call that drafts the message also researches the lead's website (per the Website Diagnostic Framework in `prompts/system.md`) and returns a `<lead_research>` block (parsed into `DraftResult.lead_research`). `pipeline.create_draft` saves this to `leads_state.research_summary`/`researched_at` and passes it back in as `prior_research` on every later generation for that lead (regenerate, next follow-up, etc.) — the model is instructed to reuse it and skip re-searching unless it looks stale or a steering note asks for something new (tools stay available, it's an instruction not a hard cutoff). Shown in the dashboard as the "About this lead" panel next to the thread (`app/static/app.js: renderResearchPanel`).
6. **Regenerate is an edit, not a rewrite.** With a steering note, the model is given **the draft currently in the editor** (`base_draft` in `POST /generate` → `pipeline.create_draft(base_draft=)` → `drafter._build_user_message(previous_draft=)`) and told to apply only that instruction, returning every untouched sentence word for word. Before this it received the note alone — the old draft was marked `skipped` and never shown to the model — so "shorten the second paragraph" produced a completely different email, because there was no second paragraph in its context to shorten. The text sent is the editor's live content, not the stored `body_html`, so hand edits survive a regeneration. Regenerating with an **empty** note keeps the old behaviour by design (it means "this one didn't land"), and the model is told to change the angle rather than reshuffle. `renderDraftSection` clears `state.originalHtml` on a lead with no draft — those variables persist across leads, so without it a first generation would be handed the previously viewed lead's message. The Batch API path (`build_batch_request_params`) never passes one; there is no prior draft to revise there.
7. **Review** — draft appears as an editable card (triage summary, English translation, edit body incl. signature, thread history). Every thread message shows the mailbox it actually came from (`msg-from`, fed by `from_email` in `_thread_payload`) — for a lead's reply that's frequently a real person answering outreach that went to a generic `info@`. The lead's first name is correctable in place (**✎ Rename** → `POST /api/leads/{cid}/{lid}/name`), which sets `leads_state.name_locked=1` so the next scan doesn't revert it to Smartlead's imported `first_name` (`scheduler._process_lead`) **and pushes the correction back to Smartlead** (`smartlead.update_lead` → `POST /campaigns/{cid}/leads/{lid}/`). It used to be dashboard-only, so the two disagreed forever: Smartlead's own sends kept merging `{{first_name}}` as the wrong name and its inbox kept showing it. Order matters — the local save and the lock happen **first**, then the push, fail-soft: a rejected call must not lose the correction, and the lock is what keeps the right name when the push didn't land. The response says which halves happened (`smartlead_synced` / `warning`, rendered as an amber line under the name) rather than reporting success for a half-done rename, and **the Smartlead half is skipped under `DRY_RUN`** like every other write. ⚠ The endpoint itself is **unverified against the live API** — field names and partial-update semantics come from Smartlead's reference, which has been wrong before; see `docs/smartlead-api.md` for the probe to run and what to check (`custom_fields` survival above all). Actions: Send now, Schedule, Regenerate (with an optional steering note), Skip, Stop following up this lead. Timing rule by kind: **replies send now** (speed-to-lead), **follow-ups schedule** — the Schedule picker pre-fills with the lead's next weekday ~9am in the campaign timezone (`thread_utils.next_morning_send_utc` off `leads_state.timezone_guess`, surfaced as `draft.suggested_schedule_at`); the client converts the picked local time to UTC before posting (`scheduleDraft`), so schedules fire when intended.

    **A scheduled lead leaves the inbox** (`db.list_inbox`). It used to sit in both tabs, still wearing its amber "Follow-up due" chip: the chip is `leads_state.category`, which the scan recomputes from the thread, and a scheduled email hasn't been sent yet — so the thread is unchanged and the detector still, correctly, says the lead is due. `_process_lead` writes that category *before* its `has_open` check, and `has_open` only ever suppressed a duplicate draft, never the chip. So `list_inbox` now excludes any lead with a `scheduled` draft. Two deliberate limits: only `scheduled` hides a lead (a `pending` draft is one waiting for review, which is what the inbox is *for*), and `category IN ('reply','auto_reply')` overrides the exclusion — if the lead answers while a follow-up sits queued, they come straight back into the inbox instead of staying hidden until the scheduled time arrives and `_send_due_draft` aborts the send. `main._open_draft_set`, which backs the green ready-dot, narrowed to `pending` for the same reason.
8. **Recipients** — the draft card shows an editable **To** and **Cc** row directly above Send/Schedule, so nothing goes out to an address that wasn't seen first (`renderRecipients` in `app/static/app.js`, built server-side by `main._recipients_payload`). **To** defaults to the address the lead last *wrote from* (`detector.next_reply_to`), not the imported `leads_state.email` — those differ exactly in the `info@` case above. **Cc** defaults to the thread-derived list (`detector.next_reply_cc`) and is where extra recipients go. Edits are stored as `drafts.to_override` / `drafts.cc_override` and are honoured by both the immediate and the scheduled send (`_send_due_draft`); `NULL` means "never edited, use the auto-derived value", while an **empty `cc_override` is a real value** meaning the auto Cc was deliberately cleared. `main._clean_cc` normalizes the free-text boxes into bare comma-separated addresses and silently drops anything that isn't one — a malformed Cc fails the whole send.

9. **Send** — `app/smartlead.py: reply_to_thread`. POST `/campaigns/{id}/reply-email-thread` body is `email_stats_id` (required — Smartlead's internal id, captured as `NormalizedMessage.stats_id`/`drafts.reply_stats_id`, distinct from `reply_message_id` the RFC822 header value), `email_body` (required), `reply_message_id`/`reply_email_time` (optional but sent for threading), plus `to_email` and `cc` from the recipients row. **`to_email` is always sent explicitly** (verified accepted against the real API 2026-07-21): the reference says To otherwise "defaults to lead email", i.e. the *imported* address — wrong whenever a real person replied from their own mailbox. Sending it explicitly makes the address shown in the dashboard the address that actually receives the mail. The same reference also documents `bcc`, `scheduled_time`, `add_signature` and `attachments` as valid optional fields; none are used yet. **`lead_id` is not a valid field on this endpoint and gets rejected** ("lead_id is not allowed") — confirmed against Smartlead's own reference and a real 400 in production; don't add it back. On success the endpoint returns **plain text** (`"Email added to the queue, will be sent out soon!"`, `content-type: text/html`), not JSON — `smartlead._request` checks `content-type` before calling `.json()` for exactly this reason. `_send_due_draft` re-fetches the thread fresh right before sending (for the race-check) and uses that fresh `last.stats_id` rather than the value stored on the draft, so older drafts (predating the `reply_stats_id` column) don't send a NULL. Re-checks the thread once more immediately before sending — for a reply/autoreply draft this only aborts if the lead has a *newer* reply than the one the draft addresses (comparing `message_id`), not merely "last message is a reply", since that's always true for a reply-kind draft by definition.

10. **Message templates** — the canned follow-ups behind "Choose a template…" live in the `message_templates` table and are added/edited/reordered/deleted from the modal itself (`GET|POST /api/templates`, `PATCH|DELETE /api/templates/{id}`, `POST /api/templates/{id}/move`; every mutating route returns the whole fresh list so the client never reconciles by hand). They used to be a hardcoded array in `app.js`, so a wording change meant a deploy. `app/message_templates.py: DEFAULT_TEMPLATES` is **seed-only**: `db.init_db` checks whether the table existed *before* running the schema and seeds only on first creation, so templates Andrew deletes never come back on restart. Placeholders are `{name}`, `{company}` and `{companyNickname}` (`message_templates.PLACEHOLDER_KEYS`), stored raw in the template. **Their values are computed server-side** (`placeholders_for`, shipped on `lead.placeholders`) and the client only substitutes — the two used to be computed independently and `{companyNickname}` existed in neither, so it was mailed to the lead with the braces still in it. `message_templates.fill` **deletes** any placeholder it doesn't know rather than leaving it, and `candidates.quick_followup` runs it again server-side as the last step before the text becomes a message. **Which language a template goes out in** is decided by `app/lead_language.py` — see §18, which is the one place the ranking lives.

    `company_nickname()` derives the spoken form of a company name (cuts at a separator, then alternately strips trailing legal forms and dangling `&` — "Sonnenplus Energie GmbH & Co. KG" → "Sonnenplus Energie"); it is deliberately conservative, since a nickname that's merely the full name reads fine and a wrong one doesn't.

11. **Images in a draft** — paste a screenshot straight from the clipboard, drag a file onto the editor, or use the toolbar's "Image" button: the file is POSTed to `/api/uploads` (authed), sniffed by magic bytes (PNG/JPG/GIF/WEBP only, ≤8 MB, `app/uploads.py`) and written to `UPLOAD_DIR` (`/data/uploads`, same Docker volume as the DB). It's inserted as an absolute `PUBLIC_BASE_URL/i/<random>.<ext>` URL. **`GET /i/{name}` is deliberately the one unauthenticated read route** — the recipient's mail client fetches it with no session; the random filename is the capability, and the name is regex-validated before touching the filesystem. Pasting a bare image URL (the old imgur route) also becomes a real `<img>` rather than link text. Clicking any image in the editor opens a floating resize bar (S/M/L/Full presets + slider) which writes the pixel size to **both** the `width` attribute and inline `style` — Outlook ignores CSS width on images — with 100% capped at 600px. The selection outline is a CSS class stripped in `editorSerialize` so it never ships in `body_html`.

    **Images in the thread view** (`app/email_clean.py`) — `clean_email_html` reduces a message body to plain text and rewraps it in its own `<p>`/`<br>`, which is what makes it XSS-safe, but `_TAG_RE` deletes every tag and an `<img>` has no text content: an image used to vanish with no gap, so a screenshot Andrew pasted was invisible the moment the draft became a sent message, and an image a lead sent was never visible at all. So each `<img>` is swapped for an alphanumeric token *before* the text reduction (`_tokenize_images` — alphanumeric so `unescape`, the whitespace collapse and `escape` all leave it alone) and rebuilt after (`_rebuild_img`) from an allowlist: `src` and `alt`, nothing else. Dropping every other attribute is the safety property — `onerror=`/`onload=` can't survive the round trip, and the output still contains only tags this module writes itself. `src` must be `http(s)` or a `data:` image (not `svg+xml`, a script carrier); anything else, including the `cid:` of an inline MIME attachment Smartlead's `email_body` doesn't carry, renders as a muted `[image]` marker so the reader knows something was there. **Remote images are deliberately allowed to load** — a lead's screenshot lives on their server, and Andrew's call is that seeing it beats hiding it, accepting that a tracking pixel in a signature will mark the thread read. Tokens inside quoted history get cut with it, so a bubble doesn't show the signature logos of every message beneath it. Non-image bodies come out byte-identical to before, and `to_plain_text` is untouched — previews, language detection, translation hashes and the campaign analysis all still see image-free text.

    **Width is part of the allowlist, and it has to be** (`_intended_width`). The signature logos state their size *only* in inline `style` (`width: 100px` and `width: 128px` in `signatures/andrew.html`), and the editor's resize bar writes it to both the `width` attribute and the style. The first version of this dropped both, so every signature logo rendered at its natural size — bounded only by the bubble's `max-width: 100%`, i.e. enormous, on every single thread. So a bare pixel number is read out of the style (or the attribute) and re-emitted by us, clamped to 600px: no sender CSS is passed through, so nothing can be smuggled through `style`. `max-width`/`min-width` deliberately don't match, and a `%` width isn't a pixel size. An image that states no width gets `.msg-img-unsized`, which the stylesheet holds to a 180px-tall strip — the raw-screenshot case, where nothing declared an intent and one image would otherwise take over the thread. Clicking any image opens it full size.

    **Bold in a draft, and `**markers**` as the way to ask for it.** A lead skims before reading, so the drafts single out the one phrase worth landing on. The rule lives in `prompts/human-writing.md` ("Bold the line that matters": one span per email, the specific thing not the sentence, never the greeting/sign-off/link, bold nothing if nothing earns it) — so it binds every generating path at once, for every client — `clients/aerodefense/prompts/` has no `human-writing.md` of its own despite what the AeroDefense section below says, so it falls back to this file. The rule therefore carries its own carve-out: approved client copy gets no markers added, since bold isn't yours to add to a sentence somebody already signed off. The model writes `**like this**` and never HTML, because everything it produces arrives as plain text and goes through `thread_utils.linkify`, which **escapes** it — a literal `<strong>` from a model would reach the lead as visible tag source, and that escaping is exactly what makes an untrusted body safe to render. `thread_utils.render_emphasis` converts the markers (called from `text_to_html`, so every draft path gets it: interactive, batch, webhook auto-reply, quick templates and localized bodies) and **deletes any unpaired `**`** — same call `message_templates.fill` makes for an unknown placeholder, since a marker that reaches the lead as literal asterisks is worse than no emphasis. Pairing is line-bounded so a forgotten closer can't bold the rest of the paragraph, and `*` joined `_URL_TRAILING` because `**https://calendly.com/x**` otherwise put the asterisks inside the `href`. The editor's **B** button already produced real `<strong>`/`<b>`, and `editorSerialize` keeps it, so hand-bolding and model-bolding land in the same `body_html`.

    The **round trips carry the emphasis rather than flattening it** (`thread_utils.html_to_marked_text` — `to_plain_text` with bold kept as `**`). Three paths hand a draft back to a model, and all three used to strip it silently: the English tab's translation, Apply-English (`localize_draft`), and a regenerate that passes the editor's live content as `base_draft` — "shorten the second paragraph" would come back unbolded. So `translator._SYSTEM` and `writing_rules.short_rules()` both say to keep the markers where they are; the English tab renders them back through `render_emphasis` so both tabs show the same emphasis. In the **thread view** `email_clean` reconstructs bold the same way it reconstructs images (`_tokenize_bold` → `_balance_bold`), because `_TAG_RE` deleted `<strong>` with everything else: a draft's bold vanished the moment it became a sent message. The tag is re-emitted with **no attributes at all**, and `_balance_bold` drops any tag whose partner the quoted-history cut took, which would otherwise bold the rest of the bubble. `to_plain_text` is untouched, so previews, language detection and translation hashes still see marker-free text.

12. **File attachments, and the library they come from** (`app/library.py`) — the draft card has a **Files** row under To/Cc: "+ Attach a file" opens a picker of documents kept **on the server**, so sending the partner-program PDF is two clicks and never involves finding it on a laptop. Attached files show as chips (click to open, × to remove) and are listed above Send, for the same reason the recipients are — nothing leaves that wasn't seen first.

    **Smartlead does not accept an upload.** `reply-email-thread`'s `attachments[]` takes a `file_url` that **Smartlead's own servers fetch** (verified end to end 2026-07-31 — the probe's PDF arrived in the recipient's inbox; `file_size` is accepted then dropped). So every attachable file must sit behind a public, sessionless URL, which is why `GET /f/{slug}` is the **second** deliberately unauthenticated read route after `/i/{name}`, and for a stronger reason: if it needed auth, attachments could not work at all.

    The library has **two sources, one list**: `clients/<slug>/source-docs/` ships in the image (`COPY clients ./clients`) and is versioned in git, so the AeroDefense PDFs are simply *present* on a fresh container; `/data/library/` holds files uploaded from the dashboard, on the same volume as the DB, which is how a new PDF gets added with no commit and no deploy. Uploads win a slug collision, so a shipped file can be superseded without one either. Shipped files can't be deleted from the UI — they'd come back on the next deploy.

    A file is addressed by a **slug** (`"AeroDefense Partner Program (1).pdf"` → `aerodefense-partner-program-1.pdf`) because the real names carry spaces and parentheses. `library.resolve` never joins the slug onto a path: it looks it up in a freshly-built map of files that actually exist, so a traversal attempt simply isn't in the dict — the same property `uploads.resolve` gets from its regex, reached differently because these names are human, stable and not secret. **Stable is required**: a sent email references the URL forever.

    **The client sends slugs, never URLs** (`main._attachment_updates`). That direction is the security property — a client-supplied `file_url` would let anyone point Smartlead's fetcher at any address and mail the result out under Andrew's name. Slugs are resolved against the library's own listing; one that doesn't resolve is dropped with a warning rather than failing the send, since the card already showed what was attached. The resolved list is stored as JSON on `drafts.attachments` rather than re-resolved at send time, so a scheduled send ships exactly what was reviewed. A missing key means "leave it alone"; `[]` means Andrew removed them. `scheduler.draft_attachments` decodes it fail-soft (a garbled column sends the message without files rather than aborting a fine email), and a draft with no attachments produces a payload byte-identical to before. **Regenerating starts a new draft row, so its attachments reset** — re-attach after a regenerate.

13. **Export for LinkedIn** (`app/exports/sheet_export.py`) — when a lead stops answering email, the next move is LinkedIn, and the worklist for that is a Google Sheet Andrew keeps by hand: one spreadsheet per client (`LINKEDIN_SHEET_ID`), one tab per sending persona (Andrew/Mia for Mindaptive, Max/Amy/Andrew/Other for AeroDefense). The button sits in the lead-actions row of the detail pane and appends the open lead as a row: `smartlead.get_lead` + the thread, `lead_export.build_row` for the fields, `sheets.append_row` for the write. It runs in a background thread and the client polls, like bulk generate.

    This is the **per-lead half of `app/exports/lead_export.py`**, which sweeps a whole account into per-persona CSVs and can only run from a laptop (`scripts/` isn't in the Docker image). The field-picking rules — which `custom_fields` alias wins, the website blocklist, the Haiku thread summary — are shared through `build_row` so the two can't drift. `_qualifies()` (3+ follow-ups since the lead's last reply) is deliberately **not** applied here: a manual click is the judgement call.

    **The tab comes from whoever's mailbox carried the thread**, not from the lead: `detector.last_sender_email` → `signatures.persona_tab`, which reads the persona's signature file and takes the first word of its stem (`max-west.html` → `Max`, `mia.html` → `Mia`), overridable with `sheet_tab` in `personas.json`. Matched case-insensitively against the spreadsheet's real tab titles. A mailbox that resolves to no persona — AeroDefense's retired `anna@`/`linda@`/`lexi.r@`, which Smartlead's `/email-accounts` no longer returns — goes to `LINKEDIN_SHEET_FALLBACK_TAB` (`Other`), created with a header row if the sheet lacks it, and the **`persona` column then names the real sender** (`Anna`, `Linda`, `Lexi`) via `client_assets.prior_senders()` reading `clients/aerodefense/prior-senders.json`. That map used to be hardcoded in `scripts/export_aerodefense_leads.py`; it moved because `clients/` ships in the image and `scripts/` doesn't, and the script now reads the same file.

    **Columns are matched against the sheet's own header row, never by position.** Andrew keeps un-headered notes in column K and colours rows by hand; writing by index would eventually land on one of them. An unrecognised header gets a blank cell, so a column added to the sheet is simply left alone, and only `persona` needs an alias (`ExportRow.sender_name`). Appends use `values:append` with `INSERT_ROWS`, so nothing existing is ever written — no formatting, no strikethrough, no notes.

    **A lead is never exported twice.** The target tab's email column is read first and a match aborts with "Already in the Max tab (row 9)". Keyed on email (the one field never rewritten by hand) and both the work and personal address count, since a duplicate row means someone gets messaged twice. The in-flight `set` in `export_lead_in_background` stops a double-click racing two appends past that check.

    **A missing LinkedIn URL is researched** (`find_linkedin`) — one Anthropic call, `web_search` only, `max_uses: 2`, `allowed_callers=["direct"]` (mandatory: AeroDefense runs Haiku, which 400s without it), 3 pause_turn turns. The result must match `linkedin.com/in/`; a `/company/` page or anything unparseable becomes `""`. Fail-soft throughout, like `_summarize_thread`: a wrong URL gets messaged, a blank one is visibly missing.

    **Not gated by `DRY_RUN`** — it writes to Andrew's own spreadsheet and mails nobody, and gating it would make the feature untestable locally, where `DRY_RUN` stays on.

    **Auth is OAuth, not a service account** (`app/google_oauth.py`): Andrew owns both spreadsheets, so acting as him means nothing to share and no key file to place on the droplet. The refresh token lives in `app_settings` (same table as `default_model`), obtained by clicking "Connect Google Sheets" — which is what the button renders as until it's set. `GOOGLE_REFRESH_TOKEN` in `.env` overrides it so the second container can reuse the first's consent (separate databases). `access_token()` caches in-process; an `invalid_grant` is translated into "click Connect Google Sheets again" rather than surfaced raw. No SDK — `app/sheets.py` is five REST calls over httpx, so `requirements.txt` and the image's pip layer are untouched.

14. **Campaign analysis** — dashboard "Campaigns" tab: which outbound message variants actually earn replies, and how to build the next run. Three tabs, all cached in the DB behind one **Analyze** click (`POST /api/campaigns/{id}/analyze` → background thread, same reason as bulk generate; the client polls `/report` while `status='running'`). **Overview** = the numbers and the emails, **Conversations** = what the replies say, **AI analysis** = the one-screen brief.
    - **What each message actually says** (`app/campaign_copy.py`) — the analysis used to rank tokens (`Icebreaker2`, `CTA1`), which is unreadable: you cannot keep a CTA you have never read. Smartlead holds the *template* on the sequence and the *values* per lead in the leads-export `custom_fields`, so this module joins them back and renders every variant as a whole readable email plus a per-slot breakdown. Three things it handles: (a) **language** — EU campaigns mail the same slot in 8+ languages, so each slot resolves to its most common *English* value (`english_score()` scores function-word share; no language-detection dependency for 5-word strings), and a campaign with no English at all gets a cached Claude translation into `campaign_slot_texts.text_en`; (b) **per-lead personalization** — a slot whose values differ per lead (`distinct/total ≥ 0.25`) has no "representative value", so all such slots are filled from ONE `_reference_lead` (most English + most complete), otherwise the rendered email came out as "the invisalign bit" over a body about dementia care; (c) per-lead data tokens (`first_name`) render as `{first name}` rather than one lead's real name.
    - **Layer 1, quantitative** (`app/campaign_analytics.py`) — the key insight is that a Smartlead A/B variant is a *recipe of slots*: campaign 3640877's six step-1 variants are all `{{subjectLineN}} + {{Greeting}} + {{icebreaker*}} + {{PitchN}} + {{OfferN}} + {{CTAN}} + {{Goodbye}}`, differing only in which numbered value each picks. Slots repeat across variants (CTA1 is in both A and C), so a slot's numbers **pool every variant that uses it** — 2-3× the sample of a six-way split. `slot_role()` buckets tokens by normalized stem so `subjectLine1`, `SubjectLine1_translated` and `Icebreaker1` all land correctly. Every rate carries a **Wilson 95% interval** and a verdict (`solid_above` / `leaning_*` / `not_enough_data`); with ~40 human replies split six ways most rows are honestly `not_enough_data`, and the UI renders that neutral grey so it never reads as a result.
    - **Two funnel stages, two metrics** (`ROLE_STAGE` / `STAGE_METRIC`) — Andrew's framing, and it decides which number is allowed to judge which part of the email. Subject line and icebreaker are all the reader sees before deciding to answer, and with open tracking off the **reply rate is our only proxy for "this got opened and read"** — so those are judged on it. Pitch/pain point/proof/offer/CTA sit below that decision, so judging them on reply rate would just re-measure the subject line above them; they are judged on **positives per reply** (`positive_per_reply`, a denominator of repliers, hence its own thresholds `MIN_CONVERSION_TRIALS`/`MIN_CONVERSION_SUCCESSES`). This is what separates "variant B is worse" from "variant B's subject works, its CTA doesn't".
    - **`recommendations()` decides; the AI only explains.** Per role it ranks slots on that role's own metric, compares the leader against the *pooled rest* by Wilson interval (`_separation`: `clear` if the leader's low clears the field's high, `leaning` only if the leader's low still beats the field's point estimate — a bare 1.0% vs 0.8% ratio does not qualify, and without the "leader must not be `not_enough_data`" guard every role on 3640877 came back "ahead, not proven" off 2 positives), and emits a `next_test` plan: hold the resolved slots fixed, vary the single highest-leverage unresolved one, `required_per_arm()` sends each. It is deterministic on purpose — a recommendation that rewords itself every regeneration is not a recommendation. The Overview panel renders this directly, before any AI has run.
    - **Positive = any `Interested*` category or a booked meeting** (`POSITIVE_PREFIXES`, guarded by `NEGATIVE_CATEGORIES` so "Not Interested" can't match). The magnet categories ("Interested for video/toolkit/calculator") used to be excluded, which left 0-5 positives per variant on a six-way split and collapsed every comparison to `not_enough_data`. `is_booked()` stays narrow ("Meeting Booked" only — "Meeting Request" is someone asking for one).
    - **Layer 2, qualitative** (`app/campaign_conversations.py`) — pulls the full threads of leads who answered *like people* (every category except Auto-Reply / Out Of Office / bounces; Not Interested and Do Not Contact are kept — a rejection is informative), then a map/reduce Claude pass extracts per-conversation objections, requested lead magnets, tone and triggers. `conversation_insights()` then aggregates those into the **win/loss split** the Conversations tab leads with — every intent, objection and asset counted separately for the conversations that ended positive and the ones that didn't, plus the quoted trigger lines from each side. The tab used to be a bare list of 44 threads, which answered nothing; the list is still there, collapsed, so a quoted claim can be checked. `first_reply_after_step` (from `email_seq_number` on our sent messages) answers "how many follow-ups still work" — on the Dental campaign step 2 outperforms step 1 3:1.
    - **Extractions are versioned** (`_EXTRACT_VERSION` in `campaign_report.py`, stored as `_v` in `extract_json`). They are cached per conversation and only re-run when the thread changes — so adding a field to the extraction prompt (`trigger_en`, the English rendering of each quote) would otherwise never reach the conversations extracted before it existed, which is most of them. Bump the version when the schema changes.
    - **Reports: one short brief, not an essay.** `directives_md` (AI analysis tab) is Do this / Don't do this / This audience / Next test, capped at about one screen, and is fed BOTH the statistics-with-copy and the conversation extractions. It replaced `report_md`, a seven-section essay that restated the data instead of saying what to type; the column survives in the schema but is never written and is cleared on each run. `conversation_md` moved to the Conversations tab and was rewritten to contrast wins against losses rather than list themes. Both prompts are forbidden from mentioning any language as a factor — it was never measured — and quotes are shown from `trigger_en`.
    - **Attribution is sequence-wide, not step-wise.** Only step 1 has variants, so a reply at step 2 still belongs to the variant that opened the thread. Scoring step-1 rows alone threw away two thirds of the evidence (14 human replies instead of 42).
    - **Open rate does not exist here.** Tracking is off account-wide (`DONT_EMAIL_OPEN` / `DONT_LINK_CLICK`) because pixels hurt deliverability, so `open_count` is 0 on every row. Replies are the only signal, and both prompts are explicitly forbidden from mentioning opens or clicks.
    - The variables come from Smartlead itself — `leads-export`'s `custom_fields` column is the source spreadsheet, so no CSV upload is needed. See `docs/smartlead-api.md` for the two counting traps in `/statistics` that this depends on getting right.
    - **Multi-account** (`app/accounts.py`): the analysis tab works for any Smartlead account, not just Mindaptive. `SMARTLEAD_API_KEY` is the default account; every `<NAME>_SMARTLEAD_API_KEY` env var adds another (slug `<name>`, e.g. `AERODEFENSE_SMARTLEAD_API_KEY` → "Aerodefense"). A switcher at the top of the Campaigns list picks the account; `GET /api/campaigns?account=<slug>` and `POST .../analyze` (`account` in body) route to that key. The account is pinned for the whole analysis via `smartlead.use_account()` — a ContextVar `_active_api_key` that `_request` falls back to, set **inside** the background worker thread (it doesn't inherit from the spawning request). Only this analysis surface is multi-account; the responder side (inbox/drafts/scan/send) stays Mindaptive-only on `settings.smartlead_api_key`. Campaign IDs are unique per Smartlead platform (a Mindaptive key 404s on an Aerodefense campaign), so the shared `campaign_*` tables need no account column.

15. **Stats** — dashboard "Stats" tab (`GET /api/metrics`, rendered by `renderStats` in `app/static/app.js`): meetings booked (from `leads_state.booked_at`), sends by kind, follow-up→reply rate (proxy: a reply-kind draft created after the follow-up's `sent_at`), avg lead-reply→our-send hours, current pipeline counts, and drafts per model (`drafts.model`, NULL for manual/template drafts). All derived from existing tables — no separate event tracking.

16. **Model picker — two providers** (`app/models_registry.py`) — the dropdown above Generate/Regenerate offers **Anthropic** and **OpenRouter** models side by side, grouped in `<optgroup>`s by provider, each labelled with its live `$in/$out per M tokens`. `models_registry.py` is the single source: the dropdown, the `is_allowed()` validation on every request-supplied model, and the default-model setting all read from it.
    - **Provider is derived from the id**, not a stored column: Anthropic ids are `claude-*`, every OpenRouter id is `vendor/model`, so `provider_for()` splits on the `/` and `drafts.model` keeps storing the plain id it always did (Stats' per-model breakdown gets OpenRouter rows for free).
    - **Anthropic prices are hardcoded** in `ANTHROPIC_MODELS` (they change rarely); **OpenRouter prices are fetched live** from `https://openrouter.ai/api/v1/models` and cached 12h in-process, with `_OPENROUTER_FALLBACK` as the offline snapshot. A stale hardcoded price is the one thing that makes a cost-comparison picker actively misleading, hence the live fetch.
    - **The OpenRouter list is curated** (`CURATED_OPENROUTER_MODELS`), not OpenRouter's full ~340-model catalog — a 340-entry dropdown is unusable. Add an id there, or to `OPENROUTER_MODELS` in `.env` (appended to the curated list), to try a new model without a code change.
    - **OpenRouter drafts have no web search/fetch and no prompt caching** (`app/openrouter.py`): it's the OpenAI chat-completions shape, one POST, no pause_turn tool loop. `drafter._generate_via_openrouter` therefore builds the user message with `use_web_search=False`, which instructs the model to reuse `leads_state.research_summary` or leave `<lead_research>` empty rather than inventing facts — research a lead once on an Anthropic model and every later OpenRouter draft reuses it. The dashboard's Web-search checkbox disables itself when an OpenRouter model is picked. The output contract (`<triage>`/`<draft_original>`/`<draft_english>`) is identical, so `parse_draft_response` and `store_draft_result` are shared with the Anthropic path — verified end-to-end against DeepSeek V4 Flash on the Jones test lead, 2026-08-05.
    - **Default model** — "☆ Set as default" next to the dropdown writes `app_settings.default_model` (`POST /api/models/default`); `models_registry.default_model()` reads it and falls back to `ANTHROPIC_MODEL`. It's the model used whenever nothing is explicitly picked: the daily scan's auto-drafts, the webhook reply path, and the dropdown's initial selection. Stored in the DB so it survives a restart with no redeploy.
    - **Anthropic-only paths use `resolve_anthropic()`, never `resolve()`** — the overnight Batch API (`app/batch_gen.py`, `drafter.build_batch_request_params`) and the cheap thread translations are Anthropic APIs, so an OpenRouter default must not leak into them or they'd 404 on a `vendor/model` id. `resolve_anthropic()` falls back to `ANTHROPIC_MODEL` when the default is an OpenRouter model. `translator.localize_draft` is the exception that *does* dispatch to OpenRouter: it runs off this same dropdown, so "Apply to draft" has to honour whatever was picked.

17. **Sorting incoming replies** (`app/reply_classifier.py`) — one word in, one word out on every inbound reply: `INTERESTED`, `AUTO_REPLY` or `NOT_INTERESTED`. This is the job the n8n workflow's gpt-5-mini node does before forwarding; it lives in the app so the catch-scan stops spending a draft on every autoresponder, so the inbox isn't buried in them, and so Smartlead's webhook could point straight at `/webhooks/smartlead` with nothing in between. Runs on `ROLE_CLASSIFY` — the Models panel row "Sorting incoming replies", defaulting to DeepSeek V4 Flash ($0.14/$0.28 per M), the cheapest model in the picker.

    **The verdict never decides visibility.** `db.mark_lead_replied` records and shows the message first; the classifier only decides whether to spend a draft and where the row sits. A classifier is exactly the wrong thing to put in front of "can Andrew see his mail". It also **fails open** to `INTERESTED` — no key, a timeout, an unparseable verdict — and it classifies `to_plain_text` output, not raw HTML, which n8n does not do (its gate has been handed `<div dir="ltr">…` markup and a signature's `googleusercontent` image URL as the message).

    **`db.sort_replied_lead` acts on the verdict, and is deliberately asymmetric.** `auto_reply` re-labels the lead into the grey tier and returns `status` to active; `not_interested` **also only re-labels**. It used to archive the lead and set `status='stopped'`, and that was reverted the same day: the model filed a lead asking about minimum deal size, and one handing over their director's address, under "no", and two rounds of prompt tuning traded those errors for others (teaching it that a redirect is a lead made it call an out-of-office a rejection). The split is by *risk*, not confidence — on the same samples it is 7/8 on autoresponders with **0/6 live conversations wrongly greyed out**, while the interested/not-interested boundary is a judgement a person should be making. Don't re-add the archiving; the full account is in `docs/reply-visibility-log.md`.

    `max_tokens` is 2048 for a one-word answer on purpose: a reasoning model bills thinking against the same budget, and at 64 the verdict came back truncated as `"NOT_RELEV"` while at 512 one message in a 177-lead backfill spent the whole allowance thinking and failed open. Hence also the parser matching prefixes, and matching the negative first since `"NOT_INTERESTED"` contains `"INTERESTED"`. `scripts/sort_inbox_replies.py` applies the same sorting to a backlog (`--dry-run` first; `--recheck-archived` undoes the reverted behaviour).
18. **Which language we write to a lead in** (`app/lead_language.py`) — one ranking, used by every path that produces an outgoing message. Three sources know something, and each path used to consult them in its own order: that is what made translation look random.
    - **The order is: Smartlead's own per-lead field → the thread → the cached `leads_state.language` column.** The cache is last because it is the one that drifts. Measured against the live API 2026-08-11 across the 336 leads in the dev database: 186 stored codes matched Smartlead's field, **16 did not**, and 11 of those said `en` for a lead whose entire thread — their replies and our sends — was German, Dutch, Swedish, Slovak or Catalan. `create_quick_draft` read that column *first* and stopped, so every template to those leads went out in English at full confidence, with the Dutch thread it was replying to sitting in the same request. All 13 re-check correctly under the new order.
    - **The field is read live, not off `leads_state`** (`lead_language.smartlead_field` — one `GET /leads/{id}`, fail-soft). The dashboard paths built their lead dict from the DB and passed the cached column *as* `language_code`, which under this ranking would put the stale value straight back on top; the webhook built one with no language at all. Both fetch it now — they already fetch a thread and then call a model, so one small GET is not what costs. Resolving also **heals the column** (`create_quick_draft` upserts when it differs), so the rest of the app stops reading the old value. The 60-second reply-catch poll (§17) deliberately doesn't: it is the cheap pass, and a lead it adopts has just written to us, so the thread answers it.
    - **Smartlead stores the code under two different custom-field names** depending on which scraper built the campaign: `language_code` (HealthClinics - EU, Dental Clinics - EU) and `targetLanguage` (SolarPanel - EU, HVAC - EU, Solar Panel - USA r2) — `smartlead._LANGUAGE_FIELDS` matches either, ignoring case and separators. Its values are trusted because they were checked: across 36 leads in three EU campaigns the claimed code matched the language of our actual outbound email every time.
    - **A third of the campaigns carry neither field** (every B2B one, Solar Panel - Germany, the HVAC USA runs; 131 of 336 leads). For them the thread is the whole answer — the lead's replies first, then **our own sent messages**, which is what took Solar Panel - Germany from 1/15 to 15/15 leads correctly resolved as `de`.
    - **The lead's replies no longer outrank the field**, which reverses the old "a Danish lead who answers in English wants English back" rule. It reads well and mails badly: it is a langdetect call on whatever they last typed, so an English out-of-office or a polite "Thanks!" flips a German clinic to English — and English is the one wrong answer that looks completely normal on the way out. Their replies still decide it whenever Smartlead has no field. To answer a bilingual lead in English anyway, regenerate with a steering note.
    - **The model is now told the language** rather than left to infer it from the thread (`drafter._build_user_message`, fed by `pipeline.create_draft` and `batch_gen`). `prompts/system.md` §9 already said "detect the thread's language and reply in it" and the model mostly obliged — mostly is the worst version when the app knows the answer outright. §9 still governs the leads where nothing does.
    - **A template that comes out in English says so** (`pipeline._quick_language_note` → `warning` on `POST /quick-draft` → an amber `.draft-note` above the editor). This path cannot fail loudly: `translator.localize_quick_text` returns its English input both when it has no language and when the call errors, so the draft looks perfectly fine until you read it. The triage line it also writes has never been rendered anywhere — `_draft_payload` doesn't carry `triage_summary` — which is why the warning goes back in the click's own response.

19. **How hot a lead is** (`app/lead_temperature.py`) — ❄️ cold / 🌤 warm / 🔥 very hot, stored on `leads_state.temperature`. A **third axis**, deliberately separate from the two statuses the app already had: `leads_state.category` (reply/followup/waiting/booked) says what the *thread* needs next, Smartlead's own lead category says how Smartlead filed the lead, and neither answers the question Andrew actually asks of the inbox each morning — *who wants to talk to us*. "Can we jump on a call Thursday?" and "please send more info" are both `reply` + `Interested`, and they are not the same lead.
    - **🔥 means they asked to talk** — a meeting, a call, a demo, their availability, a number to ring. 🌤 is a real person engaging without asking to talk yet (questions, "send more info", an objection, "check back in Q3"). ❄️ is no reply at all, or nothing but an autoresponder / rejection / unsubscribe.
    - **Two things follow from 🔥**, and they are the point of it. The lead sorts **above every other tier** in `db.list_inbox` — above a due snooze, above an unanswered reply — because the strongest signal in the account must not be buried under a dozen leads whose only claim is replying more recently. And their follow-up cadence collapses to `HOT_FOLLOWUP_WAIT_HOURS` (24h) instead of the `FOLLOWUP_WAIT_DAYS` list (`detector.decide(..., hot=True)`; it only ever *shortens* the wait). A booked lead is excluded from the promotion — the meeting is the outcome, there's nothing left to chase.
    - **24 hours needs a pass that runs more often than once a night** (`scheduler._queue_hot_followup`). The daily scan used to be the only thing that ever decided a follow-up was due, so "24 hours" would really have meant "whenever the next 6am run lands" — anywhere from 24 to 48h after the email went out, which is the entire difference between chasing someone the morning after they asked for a call and the morning after that. The 5-minute reply-catch pass already bulk-fetches every live lead's thread, so the clock is checked there for **hot leads only**, at the cost of one `detector.decide` call and no network at all. It queues a candidate rather than generating, exactly like the daily scan, so the model spend still happens on the overnight batch or on a click.
    - **The rating never cools down on its own.** It only moves up. An out-of-office from someone who asked for a call last week does not undo last week, and a lead who has gone quiet is precisely the one worth keeping in sight. The only thing that can cool a lead is Andrew, from the dropdown in the lead-actions row (`POST /api/leads/{cid}/{lid}/temperature`), which sets `temperature_locked=1` so the scan stops touching it — the same deal `name_locked` gives a corrected name. "↻ Let the AI decide" clears the lock **and re-rates on the spot**, because clearing alone wouldn't be enough: 🔥 is sticky, so the classifier would keep answering "nothing to do" and the lead would stay hot forever.
    - **One model call per inbound message, at most.** The message the rating came from is stored (`temperature_message_id`), so the 5-minute pass and the nightly scan re-read the same thread for free; a lead already rated 🔥 is never re-classified at all; and auto-reply leads are never classified, since Smartlead has already said what they are and the rating can't cool anyone down anyway. It rates the lead's **last three** messages together, not just the newest: "can we talk?" → "Thursday works" → "thanks!" would otherwise rate the thank-you and call a hot lead warm.
    - Runs on `ROLE_CLASSIFY`, the same cheap model as §17 (verified 8/8 on Haiku across English, German, an out-of-office, an unsubscribe and the three-message case). **Fails to 🌤 warm**, never hot: they did write to us, so cold is wrong, and pinning unrated leads to the top would make 🔥 mean nothing. A narrow English keyword list (`_MEETING_ASK`) is the offline fallback when there's no key or the verdict won't parse. Like §17 it **gates nothing you can see** — every reply reaches the inbox either way; being wrong costs a lead one tier of position, never a lead.

## Key config (`.env`, see `.env.example`)

- `FOLLOWUP_WAIT_DAYS` / `MAX_FOLLOWUPS` — cadence and cap. `FOLLOWUP_WAIT_DAYS` accepts a comma list (`3,4,6,8` — wait before follow-up #N, last value repeats) or a single number (old fixed cadence).
- `HOT_FOLLOWUP_WAIT_HOURS` — hours (not days) before chasing a lead rated 🔥 very hot (§19). Only ever shortens `FOLLOWUP_WAIT_DAYS`, never lengthens it; 0 puts hot leads back on the day cadence. They sort to the top of the inbox either way.
- `REVIVE_AFTER_DAYS` — after the cap, resurface a cold lead for one revival touch every N days of silence (0 disables).
- `MEETING_BOOKED_CATEGORY_NAME` — Smartlead category that freezes outreach and counts as a booked meeting (Stats view).
- `DRY_RUN=true` — pipeline runs fully but the actual Smartlead send is skipped and logged instead. Keep this on for any testing.
- `AUTO_GENERATE_FOLLOWUPS` — overnight Batch API pre-generation of due follow-up drafts (on by default; generation only, never sends).
- `AUTO_SEND_FOLLOWUPS` — autonomous mode: batch-pre-generated follow-ups go straight to `scheduled` (next lead-local weekday morning) and scheduled sends fire without review. Off by default.
- `ANTHROPIC_MODEL` — the **fallback** default drafting model (`claude-sonnet-5`); the dashboard's model picker can override it (see below). Note adaptive thinking is on by default on this model and `max_tokens` bounds thinking **plus** visible output: `app/campaign_report.py` asks for long reports and must keep `_REPORT_MAX_TOKENS` generous (an 8k budget returned a completely empty response — all of it went to thinking).
- `OPENROUTER_API_KEY` / `OPENROUTER_MODELS` — turn on the OpenRouter half of the model picker (see below). Blank key = Anthropic-only picker.
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` / `LINKEDIN_SHEET_ID` / `LINKEDIN_SHEET_FALLBACK_TAB` — the "Export for LinkedIn" button (§13). All three of the first must be set or the button isn't drawn. The OAuth client needs `<PUBLIC_BASE_URL>/oauth/google/callback` in its Authorized redirect URIs and the Google Sheets API enabled on its project. `GOOGLE_REFRESH_TOKEN` is optional and only exists to share one consent across the two containers, which have separate databases.

## Smartlead API documentation — what's actually available

**Read `docs/smartlead-api.md` before touching any Smartlead call.** It records
how to find a given endpoint's real schema and — more importantly — every place
the published docs are provably wrong.

The short version: the pages we depend on are mirrored into **`docs/smartlead/`**
(refresh via `python -m scripts.fetch_smartlead_docs`). For anything else,
`sitemap.xml` lists every page and **appending `.md` to a docs URL returns its
exact source** — fetch that, never the 670 KB rendered HTML. There is no
OpenAPI spec or Postman collection. The `SmartleadApi` file at the repo root is
**only an index** (a copy of `llms.txt`) with no field schemas — never treat it
as a spec.

**Ground truth is the live API, not the docs.** Verified 2026-07-21: the
documented response for `reply-email-thread` (`{"success": true, ...}`, JSON) is
not what it returns (plain text, `text/html`), and the documented response shape
for `message-history` is wrong in both the wrapper key and every field name.
Before relying on any field, probe it against the Mindaptive Jones test lead
(below) and record the result in `docs/smartlead-api.md`.

## Things not to change without a reason

- `app/db.py` schema (`leads_state`, `drafts`, `candidates`, `message_templates`, `app_settings`, and the `campaign_*` analytics tables) — other modules assume these exact columns.
- `app/translator.py`'s `_NATIVE_RULES` — the two localizers (`localize_draft`, `localize_quick_text`) deliberately do **not** ask for a translation. They tell the model it is a native speaker writing its own email, ban word-for-word rendering, ban literal idioms, and pin the formal/informal address. The old prompt said "just translate it naturally… do not rewrite", which produced *"Ich schließe diese Datei"* for "I'm closing this file" — a computer file — addressed with the informal *du* in first-contact outreach. `localize_quick_text` also runs on the **drafting** model, not `ANTHROPIC_TRANSLATE_MODEL`: the cheap model is for reading what leads send us, never for what we send them. `translator._SYSTEM` (incoming messages → English, for reading only) stays a faithful translation on purpose.
- `app/writing_rules.py` is the only place tone is defined. Don't add style instructions ("keep it casual", "no em dashes") to an individual prompt — put them in `prompts/human-writing.md` so every generating path gets them. The reason the module exists is that the SDR prompt, the auto-reply prompt and the localizer each carried their own half-overlapping scraps, and the translator carried none. The `**bold**` marker rule is the one thing repeated outside `human-writing.md` — `short_rules()` and `translator._SYSTEM` both carry a "keep the markers you're given" line, because those prompts rewrite text somebody already bolded and they never load the full guide.
- `smartlead._decode()` — `leads-export` returns `text/csv` with no charset, so httpx assumes UTF-8 while the file is actually Windows-1252. Without the explicit fallback every German and French lead's copy arrives with U+FFFD where its accents were ("Viele Gr��e") and that mojibake flows into the analysis as the campaign's real wording. Only guesses when the server declined to state a charset.
- The `_separation` thresholds in `campaign_analytics.recommendations` — deliberately conservative. Loosening them turns "unresolved" into "leaning" across the board, which is exactly the confident ranking of noise the confidence labels exist to prevent.
- The reply-counting rules in `app/campaign_analytics.py: _metrics` / `lead_outcomes` — `lead_category` is stamped on sends that drew no reply, and one reply appears on several step rows. Both were real bugs; only `reply_time` marks a reply, and replies are counted per unique lead.
- `app/smartlead.py` field-name guesses in `normalize_lead`/`normalize_message` — verified against the real Smartlead API response shape (nested `lead{}` object, `lead_category_id` at the top level, message-history fields `type`/`time`/`message_id`/`email_body`).
- The webhook payload shape in `app/webhook.py` (`campaign_id`, `sl_email_lead_id`, `reply_message.text`, `to_name`, `to_email`) — confirmed from the existing n8n workflow, not guessed.
- `signatures/andrew.html` / `signatures/mia.html` — real signatures pulled from Smartlead's actual sending accounts, HTML/inline-styled, not meant to be hand-edited casually. `PERSONA_FILES` in `app/signatures.py` maps a Smartlead `from_name` to one of these files.
- Smartlead API response shapes are inconsistent per endpoint (some wrap in `{"data": [...]}`, others return a bare list, `message-history` wraps in `{"history": [...]}`, `reply-email-thread` returns plain text on success) — always check `isinstance(data, list)` *before* falling back to `.get("data")`, not after (a real bug fixed in `smartlead.py`'s pagination helpers), and `smartlead._request` checks `content-type` before assuming JSON.
